# سجل الديون (MyStore)

تطبيق ويب بسيط لإدارة **ديون العملاء** في محل أو دكان صغير.
واجهة عربية (RTL) مخصّصة للموبايل، مع تسجيل دخول، فواتير دين، تسديدات، كشف حساب قابل للطباعة، وإحصائيات يومية.

**التقنية:** صفحة HTML واحدة + [Supabase](https://supabase.com) (Auth، Postgres، Realtime، Edge Functions).

---

## المميزات

- تسجيل دخول باسم مستخدم وكلمة مرور (بدون إظهار بريد Auth)
- أدوار: **مدير** و**بائع**
- فاتورة دين جديدة أو إيصال صرف نقدي
- إضافة عملاء سريعة مع حد ائتمان اختياري
- قائمة عملاء مع أرصدة الديون
- ملف عميل: كشف حركات، تسديد، إلغاء فاتورة، طباعة كشف حساب
- إحصائيات: إجمالي الديون، أكثر المدينين، آخر الحركات، ملخص اليوم
- مزامنة لحظية بين الأجهزة عبر Supabase Realtime

## إعداد قاعدة البيانات

### 1. إنشاء المشروع
أنشئ مشروعاً جديداً في لوحة Supabase.

### 2. المنطقة الزمنية

`006_stats.sql` يضبط توقيت قاعدة البيانات إلى `Africa/Tripoli` بأمر SQL، و`store_stats` يعتمد `now()::date` فيتبع هذا التوقيت.

إن منعت اللوحة تنفيذ `alter database`، اضبطها يدوياً من **Settings → Database → Timezone** قبل التشغيل — وإلا حُسبت إحصائيات «اليوم» بتوقيت UTC. غيّر القيمة داخل `006_stats.sql` إن تغيّر موقع المحل.

### 3. تشغيل الترحيلات
في **SQL Editor** نفّذ الملفات **بالترتيب مرة واحدة** على مشروع فارغ:

1. `supabase/migrations/001_schema.sql` — الجداول الأساسية، RLS، المشغّل، Realtime
2. `supabase/migrations/002_users.sql` — أسماء المستخدمين والأدوار ودالة `login_email`
3. `supabase/migrations/003_debts.sql` — حد الائتمان، فواتير الدين، التسديدات، وعرض `customer_balances`
4. `supabase/migrations/004_receipts.sql` — نوع الحركة (فاتورة / صرف)
5. `supabase/migrations/005_edit.sql` — تعديل العملاء، الحذف الآمن، إلغاء الفواتير، والأجسام النهائية المحصَّنة لـ `create_debt_invoice` و`add_payment`
6. `supabase/migrations/006_stats.sql` — توقيت قاعدة البيانات وعرض `store_stats`
7. `supabase/migrations/007_seller_void.sql` — السماح للبائع بإلغاء فواتير الدين والصرف (غير المخزنية)
8. `supabase/migrations/008_invoice_edit.sql` — تعديل قيمة وملاحظة الفاتورة للمدير
9. `supabase/migrations/009_receipt_edit_void.sql` — تعديل وإلغاء التسديدات، تمييز الحركات المعدلة، وإعادة حساب الرصيد السالب
10. `supabase/migrations/010_settlement_invoice.sql` — تحويل إيصال الصرف إلى فاتورة سداد دائنة تنقص من دين العميل

الملفات قابلة لإعادة التشغيل: تشغيل السلسلة كاملة على قاعدة قائمة لا يغيّر شيئاً. (هذا موثَّق — اختُبر على القاعدة الحيّة داخل معاملة أُلغيت.)

### 4. التحقق السريع

```sql
select routine_name
from information_schema.routines
where routine_schema = 'public'
  and routine_name in (
    'create_debt_invoice', 'add_payment', 'void_invoice',
    'rename_customer', 'delete_customer', 'login_email'
  );

select * from public.store_stats limit 1;
```

## إعداد الواجهة

في أعلى سكربت `index.html` عدّل القيم:

```js
const SUPABASE_URL = 'https://YOUR_PROJECT.supabase.co';
const SUPABASE_KEY = 'YOUR_ANON_OR_PUBLISHABLE_KEY';
const STORE_NAME   = 'سجل الديون';   // يظهر في العنوان والطباعة
```

- **SUPABASE_URL** و **SUPABASE_KEY**: من لوحة المشروع → Settings → API.
- استخدم مفتاح **anon / publishable** فقط في الواجهة (ليس Service Role).

افتح `index.html` في المتصفح، أو ارفعه على أي استضافة ثابتة (Netlify، Vercel، GitHub Pages، إلخ).

## إدارة المستخدمين (Edge Function)

الدالة `user-admin` تسمح للمدير بإنشاء وتعديل المستخدمين من داخل التطبيق.

### النشر

```bash
# من جذر المشروع بعد ربط Supabase CLI
supabase functions deploy user-admin
```

تأكد أن المتغيرات التالية متوفرة للدالة (تُضبط تلقائياً في معظم الحالات):

- `SUPABASE_URL`
- `SUPABASE_ANON_KEY`
- `SUPABASE_SERVICE_ROLE_KEY`

### أول مستخدم (مدير)

1. أنشئ مستخدماً من **Authentication → Users** في لوحة Supabase، أو عبر الدالة بعد نشرها.
2. تأكد أن سجله في جدول `profiles` له `role = 'admin'`.
3. تسجيل الدخول يتم **باسم المستخدم** (عمود `username` في `profiles`)، وليس بالبريد.

## الأدوار والصلاحيات

| العملية              | بائع | مدير |
|----------------------|------|------|
| عرض الإحصائيات والعملاء | ✓    | ✓    |
| إنشاء فاتورة / تسديد | ✓    | ✓    |
| تعديل فاتورة أو تسديد | —    | ✓    |
| إضافة عميل (بدون حد ائتمان) | ✓ | ✓ |
| تعديل حد الائتمان / حذف عميل | — | ✓ |
| إلغاء فاتورة دين/صرف  | ✓    | ✓    |
| إلغاء تسديد           | ✓    | ✓    |
| تعديل اسم العميل / حذفه | — | ✓    |
| طباعة كشف الحساب      | ✓    | ✓    |
| إدارة المستخدمين     | —    | ✓    |

الكتابة الحساسة تتم عبر دوال Postgres (`SECURITY DEFINER`) مع RLS، وليس بإدراج مباشر من الواجهة. الرصيد السالب يعني أن للعميل فائضاً لدى المتجر. العمليات المعدلة تظهر باللون البرتقالي، والعمليات الملغاة لا تدخل في الحسابات.

## التشغيل اليومي

1. افتح التطبيق وسجّل الدخول.
2. من **فاتورة**: اختر العميل، النوع (فاتورة دين أو فاتورة سداد)، المبلغ، والبيان ثم احفظ.
3. من **العملاء**: اطّلع على الأرصدة وافتح ملف أي عميل للتسديد أو الطباعة.
4. من **الإحصائيات**: راقب إجمالي الديون وآخر الحركات.
5. المدير فقط يرى تبويب **المستخدمون**.
6. من بطاقة الفاتورة أو إيصال القبض يمكن للمدير تعديل القيمة والملاحظة، مع تأكيد قبل الحفظ. الإلغاء يعيد حساب الرصيد تلقائياً.

## ملاحظات أمنية

- **عطّل التسجيل العام قبل التشغيل الفعلي**: من **Authentication → Providers → Email** اجعل `Allow new users to sign up` = **OFF**. المستخدمون يُنشئهم المدير فقط من داخل التطبيق. ما دام الخيار مفتوحاً يستطيع أي شخص إنشاء حساب ودخول المتجر.
- لا تضع مفتاح **Service Role** في `index.html` أو أي كود يعمل في المتصفح. المفتاح الوحيد المناسب للواجهة هو `anon` / `publishable`.
- `login_email` متاحة لـ `anon` (لأنها تحوّل اسم المستخدم إلى بريد للدخول) — أي أنها تكشف بريد كل مستخدم لمن يعرف اسمه. مقبول لمحل صغير، لكن يجب أن تكون على علم به.
- راجع سياسات RLS بعد أي تعديل على الجداول.
- كلمات المرور: 6 أحرف على الأقل عند الإنشاء من الواجهة.
- أسماء المستخدمين: حروف وأرقام وشرطة سفلية (وعربية في بعض الحالات)، بدون مسافات.

## إشعارات Web Push (ميزة اختيارية)

أُضيفت واجهة اشتراك للمديرين فقط، ومستقبل إشعارات في `sw.js`، وطابور أحداث داخلي. الإشعارات عامة ولا تحتوي اسم العميل أو المبلغ. عند تسجيل بائع فاتورة دين/سداد أو إلغائها يصل تنبيه للمديرين المشتركين. تنبيه حد الائتمان الافتراضي عند بلوغ **90%** من الحد، بحد أقصى مرة لكل عميل في اليوم (بحسب تاريخ UTC).

**حالة Supabase (2026-10-04):** طُبّقت الترحيلات 011 و012 و014، ونُشرت Edge Function `push-notify`. ضُبطت مفاتيح VAPID وسر Webhook في إعدادات الدالة، وخُزّنت قيمتا `push_function_url` و`push_webhook_secret` في Vault. يرسل trigger `push_events_notify` الأحداث إلى الدالة عبر `pg_net`، وتعيد مهمة `push-events-retry` المحاولة كل خمس دقائق عبر `pg_cron`. لا حاجة إلى Database Webhook في هذا المسار. لم تُنشر واجهة التطبيق المحدّثة ولم يُختبر وصول إشعار إلى جهاز؛ لذلك يلزم نشر `index.html` و`sw.js` ثم تفعيل الاشتراك من حساب مدير. أبقينا 013 غير مطبّق لتجنّب مهمة تنظيفه اليومية التي تحذف سجلات أقدم من 30 يومًا. فُحصت البيانات ولم توجد فواتير `disbursement` قديمة قبل تطبيق 011، والمنطقة الزمنية في 011 هي `Africa/Tripoli`.

### الخطوات المتبقية لتفعيل الإرسال

1. انشر النسخة المحدّثة من `index.html` و`sw.js` إلى استضافة التطبيق الفعلية عبر HTTPS؛ لا يكفي تحديث Supabase وحده.
2. افتح التطبيق المحدّث وسجّل الدخول بحساب مدير، ثم اضغط **تفعيل الإشعارات** واسمح بها على كل جهاز مطلوب. على iPhone/iPad يلزم iOS/iPadOS 16.4 أو أحدث وإضافة التطبيق إلى الشاشة الرئيسية.
3. أرسل حركة اختبار بعد الاشتراك وتحقق من وصول إشعار. عند الخروج يُحذف اشتراك هذا الجهاز ويُلغى؛ أعد تفعيله بعد تسجيل الدخول التالي.

الاشتراكات محمية بـRLS ولا تُقرأ من المتصفح مباشرة؛ تُدار عبر دوال RPC يتحقق فيها دور المدير. تزال الاشتراكات المنتهية تلقائيًا عند ردّ خدمة Push بـ404 أو 410. تعيد مهمة `push-events-retry` معالجة الأحداث غير المكتملة التي عمرها بين دقيقتين و24 ساعة، بحد أقصى 20 حدثًا في كل تشغيل؛ ولا توجد مهمة حذف مجدولة. لا تضع `VAPID_PRIVATE_KEY` أو `PUSH_WEBHOOK_SECRET` في ملفات المستودع أو واجهة المتصفح.
